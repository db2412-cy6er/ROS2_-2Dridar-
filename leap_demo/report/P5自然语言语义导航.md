## 1. 目标与验收链路

在 P4 的实时动态语义地图之上，加一层"自然语言 → 任务 → 自主导航"：

```
用户自然语言
      ↓
DeepSeek API（只做意图解析，输出结构化 JSON，绝不算坐标）
      ↓
P5 本地确定性逻辑（读取 /semantic/dynamic_map）
      ↓  数量查询 / 目标筛选 / 距离排序 / 空间关系 / 停车点几何
      ├── 普通问题 → DeepSeek 只负责把"确定事实"组织成中文
      └── 导航问题 → 生成 map 坐标系 Goal Pose
                        ↓ 出发前：ComputePathToPose + 间隙审计（≥5cm）
                        ↓ 运行中：10 Hz 间隙看门狗
                   Nav2 /navigate_to_pose
                        ↓
                   小车自主导航
```

分工是这份设计里最重要的一件事，也是写报告最站得住的部分：

| 角色 | 负责 | 不负责 |
|---|---|---|
| DeepSeek（LLM） | 把一句话理解成 `{intent, selection, rank, goal_relation...}` | 任何数字、坐标、ID、排名 |
| Dynamic Semantic Map（P4） | 实时世界模型（谁在哪、多远、哪个方位） | 决策 |
| P5 本地代码 | 计数、排序、选择、几何、安全审计 | 自然语言理解 |
| Nav2 | 规划、避障、执行 | 语义 |

**验收动作（真机三步，见 §8.3）**
1. "小车前方有几个瓶子？" → 数字必须来自本地计算；
2. "请去第三远的瓶子的右边" → 小车自主导航到该瓶子右侧 0.5 m；
3. 导航途中把目标瓶子拿走 → 任务自动取消。

## 2. 冻结契约

### 2.1 LLM 输出（唯一允许的输出形态）

```json
{
  "intent": "query_count | query_objects | navigate | cancel | unknown",
  "object_class": "bottle",
  "spatial_filter": "all | front | left | right | back",
  "selection": "all | nearest | farthest | nth_nearest | nth_farthest | id",
  "rank": 1,
  "object_id": "",
  "goal_relation": "near | left | right",
  "goal_offset_m": null
}
```

约束实现（`intent_schema.SYSTEM_PROMPT`）：明确要求"只输出合法 json、不得计算坐标、不得编造数字/ID"，并给出 8 条中英混排示例。JSON 模式按官方要求同时满足两点：`response_format={"type":"json_object"}` **且** prompt 里出现 `json` 字样与格式示例。

### 2.2 本地归一化规则（非法值一律回默认，**永不猜**）

| 字段 | 非法/缺失 → | 说明 |
|---|---|---|
| `intent` | `unknown` | `unknown` → 回答"还没定义对应操作，请换一种说法" |
| `object_class` | `bottle` | 非 bottle 也允许（结果为 0 个，并在事实里注明系统只识别 bottle） |
| `spatial_filter` | `all` | 取值域与 P4 `relation_from_bearing()` **完全一致**（±45° front，45~135 left，-45~-135 right，其余 back） |
| `selection` | navigate→`nearest`；query→`all` | |
| `rank` | `1`；`"3"`→`3`；≤0 或 >99 → `1` | 越界**不报错**，返回"没有满足条件的目标" |
| `object_id` | `""`；`selection=id` 且为空 → 降级 `nearest` | |
| `goal_relation` | `near` | |
| `goal_offset_m` | `null`；非空则 clamp 到 `[0.2, 2.0]` | 支持"停远一点/近一点" |

另外实现 **JSON 修复**：剥离 ```json 围栏 → 提取首个平衡 `{...}` → `json.loads` → 归一化；空 content 重试 1 次（官方文档明确说 JSON 模式偶发返回空内容）。

### 2.3 几何定义（冻结，避免"物体的右边"歧义）

```
u  = normalize(bottle - robot)                # 机器人看向瓶子的方向
right = ( u.y, -u.x)      left = (-u.y, u.x)  # map 系 z 向上的右手系，绕 z 转 ∓90°
near  : goal = bottle - u     * eff           # 停在车与瓶连线上，瓶子正前方
right : goal = bottle + right * eff
left  : goal = bottle + left  * eff
goal_yaw = atan2(bottle.y - goal.y, bottle.x - goal.x)   # 到达后车头朝向瓶子
eff = min(goal_offset_m, max(min_offset_m, centre_distance - 0.05))
```

**"瓶子的右边"的唯一含义**：以机器人当前看向瓶子的方向为基准，瓶子的横向右侧 0.5 m。
（该定义已用交叉积符号写进单测：right 必须 `cross < 0`，left 必须 `cross > 0`。）

### 2.4 安全常量（"≥5 cm"这条链的每一环）

| 常量 | 值 | 来源 |
|---|---|---|
| 车体外接半径 `robot_physical_radius_m` | **0.12 m** | URDF：底盘 cylinder `radius=0.10`，轮子中心 `y=±0.10`、轮宽 0.04 → 轮缘到 **0.12** |
| Nav2 `robot_radius`（硬约束） | **0.17 m** | 0.12 + 5 cm 余量（使 Nav2 的 inscribed 代价区自带 5 cm 保证） |
| 目标半径假设 `assumed_object_radius_m` | 0.04 m | P4 不输出尺寸，参数化 |
| 最小表面间隙 `min_surface_clearance_m` | **0.05 m** | 用户要求 |
| 停车距离 `goal_offset_m` | **0.30 m** | 离目标中心 0.30 m → 表面间隙约 0.14 m（四五米房间里"靠近但不撞"） |
| 最小停车距离 `min_goal_offset_m` | **0.28 m** | 配合 `xy_goal_tolerance=0.05`（P5 版 Nav2 参数）后最坏到达仍留 0.07 m 表面间隙 |
| 最小接近距离 `min_approach_distance_m` | **0.30 m** | 比这更近 → "已经在旁边，无需移动"（不发目标）。**旧值 0.75 是首轮真机"到 0.5 m 就停/干脆不动"的根因** |

**最坏情况推导**（写进离线契约测试 S20c）：`min_goal_offset - xy_goal_tolerance - robot_radius - object_radius = 0.28 - 0.05 - 0.12 - 0.04 = 0.07 m ≥ 0.05 m` ✓

## 4. 设计要点

### 4.1 两次 LLM 调用，职责完全分离

1. **解析调用**：`SYSTEM_PROMPT`（角色 `P5_ROLE=intent_parser`）→ 结构化任务；
2. **措辞调用**：把本地算好的 `FACT` 润色成中文（角色 `P5_ROLE=phraser`），提示词里明确"不得改变数字/ID/坐标，不得增加事实"。
   **第二次调用失败时直接回落到原始 FACT 文本**，机器人永远能给出正确答案。

用户提示同时携带紧凑世界状态（`P5_QUESTION=… P5_WORLD={...}`，只给 id/坐标/距离/方位/是否可见，截断到 20 个目标），token 小且模型不需要"猜"。

### 4.2 线程模型与 QoS

- ROS 回调全在主线程 executor；**LLM 调用放在 worker 线程**（否则 2 次 HTTP 会阻塞动态地图回调）；
- **单飞锁**（`single_flight`）：处理中再来指令 → 回"上一条指令还在处理"（避免两条指令产生两个 Nav2 目标）；
- 动作/服务的结果等待用 `threading.Event` + `add_done_callback`，**不**在 worker 线程里 spin（避免与主 executor 冲突）；`wait_for_server()` 在 rclpy 里只是轮询 `server_is_ready()`，可在 worker 线程安全调用（已核对 rclpy 源码）；
- 订阅 P4 用 **TRANSIENT_LOCAL**：启动瞬间就能拿到最后一条地图，不会出现"首问说没地图"。

### 4.3 出发前：路径审计（这是"不创飞矮瓶"的唯一手段）

```
1) ComputePathToPose(goal)     ← 只问路径，不动车
      └ 失败 → GOAL_UNREACHABLE（目标太靠墙/未知区）→ 降级或拒绝
2) 语义间隙审计（连续米，不受 5 cm 栅格量化影响）
      · 逐段算"点到线段"距离，要求 min(中心距) - 0.12 - 0.04 ≥ 0.05 m
      · 有低矮目标时这一步才拦得住（见 §5.1）
3) 代价地图审计（可选，默认开）
      · GetCostmap → 路径上最大格代价值必须 < 253（不进入致命/内切区）
      · 路径先按半格加密，再对每个采样点取 3×3 邻域（见 §10 的 float32 坑）
4) 通过 → 才发 NavigateToPose；不通过 → 明确告诉用户"会和谁差多少厘米"
```

### 4.4 运行中：10 Hz 间隙看门狗

- 用 TF `map→base_footprint`（不是 5 Hz 的地图回调）取实时位姿，0.2 m/s 下 0.1 s ≈ 2 cm 冗余；
- 与实时语义地图里**所有**目标算最小中心距 → 换算表面间隙：
  - `< clearance_warn_surface_m (0.05)` → `CLEARANCE_WARNING`（只报一次，不刷屏）
  - `< safety_stop_surface_m (0.00)` → `SAFETY_STOP` + `cancel_goal_async()`
- 同时记录本次任务的 **`min_surface_clearance_m`**，随任务结束状态一起发布 → 把"没撞到东西"变成可验收的数字；
- 导航超时（`nav_timeout_sec`）也会取消并报 `NAVIGATION_TIMEOUT`。

### 4.5 取消联动（P4 ↔ P5 的真正闭环）

| 触发 | 行为 | 状态 |
|---|---|---|
| P4 从动态地图删除当前目标（拿走瓶子，8 帧负观测） | 主动 `cancel_goal_async()` + 中文提示 | `TARGET_REMOVED` |
| 用户说"停下 / 取消 / 别去了" | 取消 + 提示 | `CANCELED_BY_USER` |
| 新导航目标到达时旧目标仍在跑 | 先取消旧目标再发新目标 | `PREVIOUS_GOAL_CANCELED` |
| 运行中间隙 < 0 → 0 m | 取消 + 安全停车提示 | `SAFETY_STOP` |
| 导航超时 | 取消 | `NAVIGATION_TIMEOUT` |

所有回调都带 `seq` 比对：**迟到回调不会清掉新任务的状态**（避免"旧任务结果把新任务取消"的竞态）。

### 4.6 降级策略

| 情况 | 行为 |
|---|---|
| `left/right` 目标点不可达或间隙不足 | 自动降级为 `near` 重试一次，并在回答里说明"已改为旁边" |
| 规划器不可用（`ComputePathToPose` 无服务） | **拒绝发目标**并说明（不裸发 NavigateToPose） |
| 目标 < 0.75 m | 不导航，回"已经在它旁边" |
| 未指定具体目标（`selection=all`）却要求导航 | 按最近目标处理，并在回答里注明 |
| 第二次 LLM 调用失败 | 直接输出本地 FACT |
| `robot=null`（无 TF） | 回"定位未就绪"，**绝不**输出"0 个瓶子" |
| 地图超时（> `map_timeout_sec`） | 回"地图已经 N 秒没有更新" |
| `auto_execute_navigation=false` | 只回答不控制小车（干跑演示） |


## 5. 避障与安全设计（"别把近处瓶子创飞、别撞墙、至少 5 cm"）

### 5.1 现状诊断：Nav2 本来就有避障，但当时 4 个前提不成立

| # | 硬伤 | 实测依据 | 后果 |
|---|---|---|---|
| 1 | `robot_radius: 0.10` **小于真实车体** | `xuegecar.urdf`：底盘 `radius=0.10`，但轮子中心 `y=±0.10`、轮宽 0.04 → 轮缘 **0.12 m** | costmap 认为车身 0.1 m，物理上还能再靠近 2 cm |
| 2 | **矮瓶子在 costmap 里根本不存在** | 雷达平面高度 = `base_joint z=0.076` + `laser_joint z=0.075` = **0.151 m** | 矮于 ~15 cm 的瓶子 LiDAR 扫不到 → Nav2 会直接从上面压过去（"创飞"的根因） |
| 3 | `planner_server.GridBased.allow_unknown: true` | `xuegebot.yaml` | 允许穿过**未知区域**（未建图 = 墙外/未探索走廊） |
| 4 | 没有"出发前判定"与"运行中判定" | 只有 Nav2 最后的 abort | 失败时只知道"没成功"，不知道要撞谁、差多少 |

补充量化事实：costmap 分辨率 **0.05 m**，而 `resolution` 实际传到客户端是 **float32 `0.05000000074505806`**，同一世界点在写入侧/读取侧可能落到相邻格（见 §10）。

### 5.2 三层防护

**Layer 1 · 几何硬约束（改参数即可）**
把 `robot_radius` 从 0.10 提到 **0.17**（= 物理外接 0.12 + 5 cm）。这是最关键的一招：costmap 的 inscribed 代价区边界就是 `robot_radius`，**规划器从语义上不允许路径进入 0.17 m 以内** → "≥5 cm"由 Nav2 自身保证，而不是靠调参祈祷。

**Layer 2 · 语义路径审计（P5 新增，出发前）**
先 `ComputePathToPose` 拿路径，再用**连续米**算路径与所有语义目标的间隙（要求中心距 ≥ 0.12+0.04+0.05 = **0.21 m**）。**这一步是矮瓶的唯一防线**：LiDAR 看不见 → costmap 里没有 → Nav2 会直穿 → 只有这一步能拦住并告诉用户"路径会经过 bottle_XXX，最小间隙 0.08 m"。

**Layer 3 · 运行时间隙看门狗（P5 新增，10 Hz）**
运行中如果某目标被踢到车前，间隙掉到阈值以下 → 取消任务并报 `SAFETY_STOP`；正常情况下把 **本次最小间隙** 记录下来作为验收数字。

**额外安全项**：目标 < 0.75 m 直接判定"已在旁边"不发目标（避免算出的停车点落在车身后方导致 Nav2 倒车/乱撞）。

### 5.3 Nav2 参数改动（**新建副本，P1 原文件一字未改**）

新文件：`xuegecar_navigation2/param/xuegebot_p5.yaml`（`xuegebot.yaml` 保持原样，便于回退与对比）

| 参数 | 原值 | P5 值 | 理由 |
|---|---|---|---|
| `global/local_costmap.robot_radius` | 0.10 | **0.17** | 轮缘外接 0.12 + 5 cm 硬保证 |
| `inflation_radius` | 0.20 | 0.30 | 软偏好区（必须 > robot_radius） |
| `cost_scaling_factor` | 3.0 | 2.0 | 内圈代价衰减更快，避免大片高代价导致无解 |
| `GridBased.allow_unknown` | true | **false** | 禁止穿越未知区域（防撞墙） |
| `general_goal_checker.xy_goal_tolerance` | 0.25 | **0.05** | 精确停点（配合 P5 的 0.30/0.28 停车距离） |
| `general_goal_checker.yaw_goal_tolerance` | 0.25 | **0.15** | 到位朝向更准 |
| `FollowPath.max_vel_x` / `max_speed_xy` | 0.30 | **0.05** | **5 cm/s 慢速档**（用户要求：慢而准，不许冲出去） |
| `FollowPath.min_vel_x` / `acc_lim_x` / `decel_lim_x` | −0.12 / 1.0 / −2.5 | **−0.05 / 0.2 / −0.3** | 慢速下的加减速上限 |
| `FollowPath.max_vel_theta` / `acc_lim_theta` | 1.2 / 2.0 | **0.6 / 1.0** | 转向同样要慢 |
| `FollowPath.sim_time` / `linear_granularity` | 2.5 / 0.05 | **4.0 / 0.01** | 5 cm/s 下 2.5 s 只走 12 cm，轨迹太短 |
| `FollowPath.trans_stopped_velocity` | 0.25 | **0.02** | 必须远小于 `max_vel_x`，否则 RotateToGoal 永远认为"已停住" |
| **`progress_checker.required_movement_radius` / `movement_time_allowance`** | 0.3 / 10 s | **0.05 / 30 s** | 5 cm/s 下 10 s 只走 0.5 m，旧值会把正常爬行判成"卡住"并中止 |
| **`amcl.update_min_d` / `update_min_a`** | 0.25 / 0.2 | **0.02 / 0.03** | 旧值 = 走 25 cm 才校正一次位姿；5 cm/s 下等于每 5 秒才校正一次，中间全靠里程计外推 → 语义定位全歪 |
| `amcl.do_beamskip` | false | **true** | 房间里的瓶子/人在地图上不存在，旧设置会把这些光束也拿去匹配、把位姿拉偏 |
| `amcl.alpha1..alpha5` | 0.2 | **0.3** | 这台底盘里程计噪声偏大，过于自信会跟丢 |
| `amcl.max_beams` / `laser_max_range` | 60 / 100.0 | **90 / 12.0** | 与真实雷达量程对齐，显式声明 |
| **`local_costmap.plugins`** | static+obstacle+voxel+inflation | **obstacle+inflation** | local costmap 是 rolling(odom) 窗口，挂 `static_layer` 等于把地图再画一遍并随车滑动 → RViz 上就是"地图重叠、越跑越乱"；`voxel_layer` 与 `obstacle_layer` 同源重复标记，一并去掉 |
| `global_costmap.obstacle_layer.scan.raytrace_max_range` | 3.0 | **2.5**（= obstacle_max_range） | 超过清理距离的旧标记永远清不掉，位姿差几厘米就在墙边留"幽灵墙"，越跑越花 |
| `behavior_server.max_rotational_vel` / `min_rotational_vel` / `rotational_acc_lim` | 0.8 / 0.4 / 3.2 | **0.5 / 0.15 / 1.5** | 脱困旋转更柔和 |
| **新增 `velocity_smoother` 段** | 无（落默认 0.26 m/s） | **max_velocity [0.05, 0, 0.6]** | 让 DWB→smoother→/cmd_vel 整条链都显式处于慢速档 |

启动方式（原 launch 不改，只换 `params_file`；P5 另加了 `rviz_config` 参数，默认仍是 nav2 自带视图，**向后兼容**）：

```bash
ros2 launch xuegecar_navigation2 navigation2_rviz.launch.py \
  map:=/home/chuyun/xuegeros_ws/maps/p1_cartographer_room.yaml \
  params_file:=/home/chuyun/xuegeros_ws/install/xuegecar_navigation2/share/xuegecar_navigation2/param/xuegebot_p5.yaml \
  rviz_config:=/home/chuyun/xuegeros_ws/install/xuegecar_navigation2/share/xuegecar_navigation2/rviz/p5_view.rviz
```

新增的 `rviz/p5_view.rviz`：**只显示一张地图**。实测 nav2 自带视图 `nav2_default_view.rviz` 默认同时打开 4 个地图图层（`Map` + `Global Costmap` + `Downsampled Costmap` + `Local Costmap`，另有粒子云）——它们叠在一起本来就像 "地图重叠"；而 `Local Costmap` 是 rolling 的 odom 系窗口，车一开它就在静态地图上滑动，于是 "越来越乱"。P5 视图关掉了它们，只留 `Map` / `LaserScan` / `Path` / `RobotModel` / `TF`，并新增两条语义标记：`/semantic/dynamic_markers`（P4 对象）与 `/semantic/localization_markers`（P3 每帧观测）。

**代价说明（诚实标注）**：`robot_radius: 0.17` 要求可通行宽度 ≥ 0.34 m；比这窄的门洞会**规划失败而不是硬挤过去**（安全侧）。若要更宽松，可退回 `0.13`（仅 1 cm 余量 + 靠 inflation 软避障），此时 5 cm 由 Layer 2/3 兜底。

### 5.4 尚未做、留作 P5.1 的一项

把 P4 的语义目标**注入 costmap**（发布 `/semantic/obstacle_cloud` PointCloud2 + 增加一个 observation source），让 Nav2 能**主动绕开矮瓶**，而不是"拒绝进入"。本报告把这一项放进 P5.1 的原因很具体：Humble 的 `ObstacleLayer` 对 PointCloud2 会从观测原点做 raytrace 清除，直接开 `clearing: True` 会误清 `/scan` 标记的墙格；可行做法是 `clearing: False` + 订阅 P4 `/semantic/events` 的 `REMOVE` 事件做受控清理，需要单独一轮离线验证，不应与 P5 主线混在一起。

## 9. 已知边界 / 风险 / 下一步

**已知边界（写进报告是为了不被问到答不上来）**

1. **矮于 ~15 cm 的瓶子**：LiDAR 平面在 0.151 m，Nav2 的 costmap 永远看不见 → P5 只能"拒绝进入"（Layer 2 审计），**不能主动绕行**；主动绕行需要 §5.4 的 P5.1 语义障碍注入。
2. **对墙的 5 cm**：受 0.05 m 栅格量化，实际保证是"≥1 个栅格（≈5 cm）"；对语义目标则是连续米计算，无量化误差。
3. **目标半径 0.04 m 是假设值**（P4 不输出尺寸）。瓶子更粗时把 `assumed_object_radius_m` 调大即可（参数化，不改代码）。
4. **DWB 是局部避障**：Layer 2 审计的是全局路径，局部绕行偏差由 Layer 3 看门狗兜底。
5. **P2 只放行 bottle**（`target_classes: ["bottle"]`）：问"有几个杯子"永远是 0 个，属设计范围。
6. **P4 的 `objects` 只含 `state=confirmed`**：新瓶子要连续 3 帧命中才进地图，因此"刚放上就问"可能少一个（属 P4 口径）。
7. **P4 的 `nearest_rank/farthest_rank` 在"有目标缺距离"时不可信**（它把 `None` 当 `inf` 排到最后）：P5 一律本地重排，不一致时打 `RANK_MISMATCH`，这是"不信任上游排序"的显式设计。
8. **P3 的 z 基准问题（P3 报告 §9）不影响 P5**：P5 只用 `position_map.x/y`。
9. **发布 `/llm/response` 前会等措辞调用**：正常 1–3 s；`query_deadline_sec` 到期就直接输出本地 FACT。
10. **`robot_radius: 0.17` 的代价**：可通行宽度要求 ≥ 0.34 m；窄门洞会规划失败（安全侧），可回退 0.13。
11. **真实 DeepSeek API 的"业务调用"未在本机自测**：本机没有 `DEEPSEEK_API_KEY`，所以只有"模型名发现/回退"这条路径用离线场景 S19 做了真值复现，`chat/completions` 的真正返回格式仍以现场第一次提问为准。若提问后回答是"大模型接口调用失败"，看节点日志里的 `LLM_ERROR` 具体信息（已把 HTTP 状态码与 API 错误消息一起带出来）。

## 10. 踩坑记录（工程沉淀，逐条都真实发生过）

1. **`robot=null` 会答错，不是答"不知道"**：P4 拿不到 TF 时 `relative_position/distance` 全为 `null`，"前方有几个瓶子"会算成 0 并一本正经地回答"0 个"。**确定性代码也会"撒谎"**，所以必须在进 LLM 之前显式判断定位状态（→ `MAP_NOT_LOCALIZED`）。
2. **QoS 不对齐**：P4 用 `TRANSIENT_LOCAL depth=1`，订阅端若用默认 volatile，启动瞬间拿不到 latched 的最后一帧。改成同构 QoS 后启动即可问答。
3. **`farthest_rank` 有坑**：P4 排序把 `None` 当 `inf`，一旦有目标缺距离，"第 3 远"可能落到最远的那个对象上 → P5 一律本地排序，并把不一致写进 `RANK_MISMATCH`。
4. **代价地图 `resolution` 是 float32**：`0.05` 到客户端变成 `0.05000000074505806`，同一世界点在写入侧是第 110 格、读取侧算出第 109 格 → 致命格漏检（离线测试里真实复现）。修法：路径先按半格加密，再对每个采样点取 **3×3 邻域**取最大代价。
5. **不要用中文字符串做进程间"角色"判定**：假 DeepSeek 曾用 `if '意图解析器' in system_prompt` 判断"这是解析调用还是措辞调用"，结果两个文件里看起来一模一样的汉字**码点不同**，导致 mock 一直走措辞分支、返回的 `intent` 全是 `unknown`（表象是"LLM 好像听不懂话"）。修法：契约里加 ASCII 标记（`P5_ROLE=intent_parser` / `P5_ROLE=phraser`、`P5_QUESTION=` / `P5_FACT=`），并在跑测里加一条"协议自检"场景（S0b）防止再犯。
6. **停车偏移公式**：原先用 `eff = min(offset, max(min_offset, 0.5·d))`，结果 0.8 m 外的瓶子只停在 0.4 m 处（"只停了一半"）。改成 `eff = min(offset, max(min_offset, d − 0.05))`：只要目标够远就一定停在配置的停车距离。
   > ⚠️ 这条后来被真机推翻一半：当时为了"停不准就别动"把 `min_approach_distance_m` 提到 0.75 m，结果**四五米的房间里小车在 75 cm 外直接回"已经在旁边"，一步都不走**（现场"去第二个瓶子左边 → 已经在了"）。正确做法是**让它走近**（`goal_offset_m=0.30 / min_approach=0.30`），安全性交给 5 cm 表面间隙审计，而不是靠"离得远就不动"。见第 11 条。
7. **"路径审计"真的会拒绝人**：离线 S17 原设计让车去最远的瓶子，审计算出路径会贴着 `bottle_001` 过去（间隙 −0.06 m）→ 直接 `PATH_BLOCKED`。当时我以为是 P5 有 bug，实际是**审计按设计工作**：该拒绝时就拒绝，这也是"不创飞近处瓶子"的直接体现。
8. **参数类型必须与 YAML 一致，否则节点在 launch 时直接死**：`path_max_cell_cost` 在代码里按 `double` 声明（253.0），而 YAML 写的是 `253` → `InvalidParameterTypeException`，`ros2 launch` 起来就崩。**离线跑测当时没抓到**，因为它用 `-p name:=value` 覆盖，绕过了 YAML；是靠"跑一次真实 launch"才发现的。修法：把该参数按 `int` 声明，并让离线跑测改为**加载出厂 YAML**（外加少量覆盖），把"参数文件能否被接受"纳入回归。
9. **rclpy 的日志调用点会缓存 severity**（真机首次运行踩到）：`rclpy/impl/rcutils_logger.py:287-299` 用 `CallerId = (函数名, 文件, 行号, 字节码偏移)` 记住每个调用点第一次用的 severity，同一个调用点第二次换个级别就抛 `Logger severity cannot be changed between calls.`。我原来写的是
   ```python
   getattr(self.logger, level, self.logger.info)(message)   # 一个调用点发三种级别
   ```
   于是"模型不存在 → 回退"这条 WARN 直接抛异常，被 `_log_startup` 的 `except Exception` 吞掉，打成了 `model discovery failed: ...`；**更糟的是异常抛在 `self.model = candidate` 之前，模型没被换成可用的那个**，导致之后每次提问都会因"模型不存在"失败。修法三条：①每个级别单独一行调用（各自一个调用点）；②`_log` 整体 try/except，日志失败永不影响业务；③**先赋值再打日志**。回归：新增单测 `test_deepseek_client.py`（8 例）+ 离线场景 S19/S19b（照真机日志复现）。
   > 教训：**"日志报错"往往不是日志的问题，而是它把后面的正确逻辑一起带走了。**
10. **模型名要以 `GET /models` 为准**：文档写的 `deepseek-v4-flash` 在实际账号里并不存在（真实是 `deepseek-flash` + `deepseek-v4-pro`）。因此 P5 启动时会现场核对并回退，`api_models_fallback` 三个名字都列上；同时给 launch 加了 `api_model:=...` 参数，换模型不用改文件。

### 10.1 首轮真机联调（2026-09-10）暴露的第二批问题

用户现场跑出两个现象：**"RViz 地图越来越乱、像重叠"** 和 **"前面放两个瓶子只说成一个、让它去第二个左边却说已经在了"**。逐层查下来是**三组互相叠加的原因**（不是 P5 一个包的问题），也顺带推翻了第 6 条里的 0.75 m 设计。

11. **"到 0.5 m 就停 / 干脆不动" 是 P5 自己的参数，不是 Nav2**：`min_approach_distance_m: 0.75` 意味着目标（估计值）在 **75 cm** 内就直接回 "已经在旁边，无需移动"，**一步都不发**；再叠加 `goal_offset_m: 0.50` + `xy_goal_tolerance: 0.10`，正常也会停在离瓶心 0.4~0.6 m。用户要的 5 cm 其实早已实现两处（Nav2 `robot_radius=0.17` 与 P5 的 5 cm 表面间隙审计），**唯独"停多远"没改**。→ 改为 `goal_offset_m: 0.30 / min_goal_offset_m: 0.28 / min_approach_distance_m: 0.30`，回归 S13b。
12. **5 cm/s 不是改一个 `max_vel_x` 就完事，慢速机器人有 4 个隐形门槛**：① `progress_checker.required_movement_radius=0.3` + `movement_time_allowance=10 s` → 5 cm/s 下 10 s 只走 0.5 m，**正常爬行会被判"卡住"并中止**；② `trans_stopped_velocity=0.25` 大于最大速度 → `RotateToGoal` 永远认为"已停住"；③ AMCL `update_min_d=0.25` → **走 25 cm 才校正一次位姿**，5 cm/s 下等于每 5 秒才校正一次，中间全靠里程计外推，语义定位全歪；④ `velocity_smoother` 未在 yaml 里声明 → 落默认档。→ 四处一起改，回归 S21/S21b/S21c。
13. **RViz "地图重叠"有一半是显示问题，另一半是真问题**：nav2 自带 `nav2_default_view.rviz` 默认同时打开 **4 个地图图层**（`Map` + `Global Costmap` + `Downsampled Costmap` + `Local Costmap`，另有粒子云），叠在一起本来就"像重叠"；而 `local_costmap` 是 **rolling(odom) 窗口却挂着 `static_layer`**，等于把地图在 odom 系里再画一份、随车滑动。→ 新增 `rviz/p5_view.rviz`（只留一张地图）并从 local costmap 插件里去掉 `static_layer`/`voxel_layer`，回归 S21d。
14. **地图"越来越乱"的第二个真问题：清不掉的幽灵墙**：全局代价地图 `raytrace_max_range=3.0` > `obstacle_max_range=2.5`，超出清理距离的旧标记**永远清不掉**；位姿只要差几厘米，就会在静态地图的墙旁边再描一遍，跑得越久越花。→ `raytrace_max_range` 与 `obstacle_max_range` 取齐（2.5），并且 `amcl.do_beamskip=true`（房间里瓶子/人在地图上不存在，旧设置会把这些光束也拿去匹配、把位姿拉偏）。
15. **P3 从不校验相机内参与实际图像分辨率**（这条最可能是"瓶子在正前方、地图却说在旁边"的根因）：标定 yaml 写死 800×600（`fx=456, cx=404`），而 MJPEG 推流分辨率是在相机板子上配的；P3 拿到 detections JSON 里的 `image_width/image_height` **只转抄、不比对、也不缩放内参**。一旦实际分辨率不是 800×600，"正前方"会被算成偏 10~30° 的侧向目标（离线单测量化：>5 cm，某些情形射线直接打不到地面）。→ 新增 `scale_intrinsics()`（纯函数）+ `auto_scale_intrinsics: true`：按比例缩放 fx/fy/cx/cy，宽高比不一致时打 ERROR，并把 `intrinsics_scaled / calib_width / intrinsics_fx` 写进输出 JSON 供现场核对。
16. **P4 的同帧去重门限过大**：`association_distance=0.25` 同时用于**同帧同类别去重**和跨帧关联 → 同帧里两个相距 20 cm 的瓶子（单目地面交点在 2 m 处误差可达 ~7 cm/像素）很容易被算成"同一个物体"而合并。→ 拆出独立参数 `same_frame_dedupe_distance: 0.05`（同帧的两个框本来就是两个物体，NMS 已经压掉同一物体的重复框），跨帧关联降到 0.15（既不合并两个瓶，也不让同一瓶分裂）。回归 S20。
17. **"前方"是一个 ±45° 的扇区，不是一个方向**：P4 `relation_from_bearing()` 用 `-45°..45°=front / 45°..135°=left / -135°..-45°=right`，P5 数"前方有几个"直接用它 → 摆得偏一点的那个瓶子（或位姿偏了 20°）会被归到"左侧"而不计入"前方"，于是"前面放了两个"只数到 1。**这不是 bug，是定义问题**：答复里会逐个打印每个目标的 `relative_position`，可据此判断。若要更宽松，可在 P4 调整扇区边界（属可配置口径，改动会影响"左侧有几个"这类问法，需与用户对齐后再动）。

### 10.2 现场仍需用眼睛确认定位（本机无法验证）

上面第 13~17 条里，**定位本身准不准**是唯一无法在离线环境验证的环节（离线用的是 harness 广播的理想 TF）。现场请用两个动作判定：

1. **RViz 放大到墙角**：红色激光点必须**严丝合缝压在黑色墙上**。若整体偏移几厘米或几度 → AMCL 未收敛 / 2D Pose Estimate 不准 / 雷达安装外参与 URDF（`laser_frame` 在 `base_link` 原点、z=0.075）不一致。此时**不要怀疑语义逻辑**，先重做位姿估计（RViz 的 `2D Pose Estimate` 拖准，或原地小范围转两圈让 AMCL 收敛）。
2. **`ros2 topic echo --once /semantic/objects_localized`**：把两个瓶子一前一后摆在 1 m 附近，看 `objects[]` 的 `position_base_footprint` 是否"正前 = y≈0"、距离是否与卷尺一致（±10 cm 内可接受，单目地面交点在这个距离的噪声就是厘米级）。若"正前"算出 y 明显不为 0 → 就是第 15 条的相机分辨率/内参问题，看 P3 日志里有没有 `intrinsics rescaled` 的 WARN。
