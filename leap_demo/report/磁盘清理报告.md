# 磁盘清理报告（2026-09-09）— ROS2 历史日志爆盘根因与长效治理

## 1. 现象与根因

`ros2 launch xuegecar_bringup xuegecar_bringup.launch.py` 直接报
`OSError: [Errno 28] No space left on device: '/home/chuyun/.ros/log/2026-09-09-19-48-25-...'`。

**根因（已从源码确认）**：ROS2 Humble 的 launch 日志机制
（`/opt/ros/humble/lib/python3.10/site-packages/launch/logging/__init__.py`）
每次 `ros2 launch` 都会在 `~/.ros/log/` 下**新建一个 `时间戳-用户名-PID` 目录**，
并**从不自动轮转/删除**。经年累月/高频调试后目录无限膨胀，最终写满整块根分区。

> 之后用户手动清理过，故调查时 `~/.ros/log` 仅剩 112K、`df` 显示 67~68%，
> 但这套“只增不减”的机制依然存在，必须长效治理。

## 2. 本次落地的长效治理

### 2.1 journald 系统日志（根分区 /var/log/journal，原先 656M）
- 立即释放：`journalctl --vacuum-size=200M`（释放 504M → 现存 152M）
- 永久上限（重启不丢，追加到 `/etc/systemd/journald.conf` 末尾）：
  ```
  SystemMaxUse=200M
  RuntimeMaxUse=100M
  ```
- `systemctl restart systemd-journald` 已生效；journald 达到上限后自动淘汰旧日志。

### 2.2 snap 保留策略
- `snap set system refresh.retain=2`：系统快照只保留最近 2 个版本，杜绝旧版本堆积
  （已确认 `snap get system refresh.retain` → `2`）。

### 2.3 apt 周期性自动清理
- `/etc/apt/apt.conf.d/10periodic` 写入：
  ```
  APT::Periodic::Update-Package-Lists "1";
  APT::Periodic::Download-Upgradeable-Packages "0";
  APT::Periodic::AutocleanInterval "7";
  ```
  每周自动清理已下载的安装包缓存（本次 `apt-get clean` 已把 archives 419M → 108K）。

### 2.4 ROS2 历史日志专项清扫（本次爆盘根因的核心对策）
- 脚本：`/home/chuyun/scripts/disk_housekeeping.sh`（可执行）
- 策略对 `~/.ros/log` 采用**双保险**：
  - 按年龄：删除 >3 天的会话目录（保留最近 3 天便于回查）
  - 按体积：总量 >300M 时从最旧目录删除直到 <150M（防某次调试狂刷瞬间写满）
- 附带清理：各 `*_ws/log` 下 >30 天的 colcon 构建日志、`pip cache purge`
  （只清下载缓存，不动已安装包）
- **绝不触碰**：bags / models / 源码 / 工具链 / 用户业务数据。
- 定时器：`~/.config/systemd/user/disk-housekeeping.{service,timer}`
  每天 03:00 自动执行；`Persistent=true` + `loginctl enable-linger chuyun`，
  关机错过也会在开机/登录后补跑。
- 手动运行：`systemctl --user start disk-housekeeping.service`
  运行记录：`/home/chuyun/scripts/disk_housekeeping.log`

### 2.5 保留的 ROS2 默认日志位置
未改动 `~/.ros/log` 默认目录，最近 3 天日志照常可回查。
ROS2 原生支持环境变量 `ROS_LOG_DIR`（launch 与 rcl 日志均读取）——
若将来希望“日志只进内存、重启即清”，可把 `ROS_LOG_DIR` 指到 tmpfs
（例如 `/dev/shm/ros_log`），本方案默认不启用。
